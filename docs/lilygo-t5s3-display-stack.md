# LilyGo T5 S3 Pro: the panel, LovyanGFX, and what we know

Reference for anyone touching the T5S3 display path. Consolidates
`lilygo-t5s3-refresh-audit-2026-09-15.md` (waveform banks) and
`t5s3-waveform-implementation-audit-2026-09-21.md` (vendor vs libraries) and adds what the
2026-09-22 async/overlap work established.

Read this before changing anything in `LgfxEpdDriver`, the waveform generator, or any predicate
that reads a display capability.

## 1. The stack

| Layer | What it is |
|---|---|
| Panel | ED047TC2, 960x540, 4 bits per pixel, raster-scanned via the S3 LCD peripheral |
| Library | **M5GFX**, which embeds LovyanGFX under `src/lgfx/`. Note the name: a filesystem search for "lovyangfx" finds nothing |
| Panel class | `lgfx::Panel_EPD` (`platforms/esp32/`). **Not** `Panel_EPDiy` (`panel/`), which wraps the epdiy library and is not compiled here |
| Our driver | `LgfxEpdDriver`, behind `PanelDriver` |
| Waveform | Generated by `freeink-sdk/tools/gen_ed047tc2_waveform.py` from the vendor blob into `BoardT5S3/src/ED047TC2Waveform.cpp` |

## 2. Panel_EPD is already asynchronous

`Panel_EPD::display(x, y, w, h)` does not refresh. It accumulates a dirty rect and posts an
`update_data_t` to `_update_queue_handle`; a dedicated panel task (`task_update`, pinned, 4 KB)
drives the frames. `waitDisplay()` is the join.

**The `_display_busy` race is real and has frozen a reader.** `display()` raises `_display_busy`,
yields (`vTaskDelay(1)`), and only *then* posts the job. In that gap the panel task's loop top
assigns `_display_busy = remain` -- false on an idle panel -- clearing the flag the caller just
raised. A caller that trusts it walks into the task's diff copy and tears the step state, after
which `remain` never clears and the next `waitDisplay()` blocks forever: panel frozen, input still
alive.

The discipline that avoids it, and which any split must preserve:

```cpp
void ingestDisplay() { vTaskDelay(pdMS_TO_TICKS(2)); }  // NOT the optional half
void awaitDisplay()  { g_dev.waitDisplay(); }
```

The **yield** is what makes the flag mean anything: it returns with the job owned by the panel
task, so the later wait means what it says. `displayStart()` keeps the yield; `displayFinish()` is
the wait. (History: 1.5.16 shipped the yield guard, 1.5.17 reverted it on a ghosting suspicion,
and the ghosting survived the revert -- which clears the guard of that charge.)

## 3. Refresh cost: bank length, not pixels, and not area

Duration = **bank length x ~33 ms per frame**. Independent of how many pixels changed.

It is also independent of the dirty rect. `display()` carries a sub-rect through the queue, but
the output loop scans the whole panel every frame:

```cpp
for (uint_fast16_t y = 0; y < mh; y++) {   // mh = FULL panel height
    blit_dmabuf(dma_buf, &_step_framebuf[(y * memory_w >> 1) * 2], _lut_2pixel, w);
    bus->writeScanLine((const uint8_t*)dma_buf, write_len);
}
```

**A smaller rect only shrinks the CPU staging loop, never waveform time.** `Panel_EPDiy` by
contrast builds an `EpdRect` and hands it to epdiy, which honours it -- but that path is not
compiled here.

Corollary: LovyanGFX guides written for LCD boards (`pushBufferDMA()`, `waitDMA()`, `setWindow()`)
do **not** transfer. Those are the `Panel_LCD` path. This is `Panel_EPD`, and its join is
`waitDisplay()`, not `waitDMA()`.

Measured full-refresh durations, for calibration: FAST ~1329-1559 ms, HALF ~2582-2950 ms. That is
roughly 2-4x an X4 Pro and 3x an X3, and it is why several things that are affordable elsewhere
are not affordable here.

## 4. The waveform, and the one thing LovyanGFX cannot express

The vendor blob (`ED047TC2.h` / epdiy's `epdiy_ED047TC2.h` -- same data) holds, per mode and
temperature range, a `[phases][16][4]` table: a 2-bit drive code for every **(destination, source)**
level pair, per phase. Three modes -- DU (1), GC16 (2), GL16 (5) -- across 7 ranges (blob 5..11).

`gen_ed047tc2_waveform.py` proves GC16 is exactly separable with a zero diagonal
(`net(to, from) == L[to] - L[from]`), which makes `L` the vendor's net displacement vector.

**LovyanGFX's LUT has no source term.** `Panel_EPD` expands one 32-bit word per phase indexed by
level alone:

```cpp
dst[lindex] = (((lu >> ((lv >> 4) << 1)) & 3) << 2) + ((lu >> ((lv & 15) << 1)) & 3);
```

epdiy builds the full `[to][from]` table from the same blob:

```cpp
uint8_t index = (to << 4) | (from_packed * 4);
```

and even ships a `build_2ppB_lut_64k_static_from` variant -- source assumed fixed. **LovyanGFX's
design is structurally that `static_from` mode, permanently.** Not an oversight; one point on a
spectrum epdiy spans.

Our generator compensates by making every column self-normalising: saturate at a rail first (which
erases the arrival state), then walk to the target. `clean_rows()` is `3 x L[15]` frames.

### What that costs, measured

| blob range | 5 | 6 | 7 | 8 | 9 | 10 | 11 |
|---|---|---|---|---|---|---|---|
| ours (`3 x L[15]`) | 72 | 63 | 63 | 63 | 51 | 48 | 42 |
| vendor GC16 phases | 46 | 43 | 40 | 38 | 38 | 44 | **57** |
| vendor net (`L[15]`) | 24 | 21 | 21 | 21 | 17 | 16 | 14 |

Two things to read here:

- **Vendor GC16's phase count is not a function of `L[15]`.** At range 5 it spends 46 phases to
  deliver a net of 24; at range 11, 57 phases for a net of 14 -- almost pure scrub. Physically
  sensible (warm ink moves faster, so less net drive but more settling), and our `3 x L[15]`
  formula cannot express it: too long when cold, **too short when warm**.
- **At range 11 we likely under-drive** (42 vs 57). That is a quality risk, not a speed win, and a
  standing candidate for residual ghosting.

### There is no cheap acceleration

Measured, not assumed. Forcing the source with a rail excursion and then using the vendor's
from-white column costs `L[15]` frames for the excursion, which consumes the entire saving: 69
frames vs our 72 at range 5, and **worse** at ranges 9-10. The vendor's 46 phases are cheap
*because* they are source-aware -- a pixel already near white never pays a full excursion -- which
is exactly what a destination-only LUT cannot do. Real speed needs runtime source-awareness.

### Why porting source-awareness into Panel_EPD is expensive

- **No spare index bits.** `_step_framebuf` entries are `int16` used directly as LUT indices: bits
  0-7 are two destination levels, 8-14 the bank selector, 15 the "still has work" flag
  (`blit_dmabuf` branches on sign). Source-aware two-pixel lookup needs the whole word.
- **LUT size.** `_lut_2pixel` is `lut_total_step * 256 * sizeof(uint16_t)`. Source-aware is 64k
  entries -- 128 KB per step -- read in the inner loop, so internal RAM, not PSRAM.
- **Hand-written Xtensa assembly.** `blit_dmabuf` is keyed to that exact index format.
- **No previous-frame plane.** `_buf` holds only the target. epdiy has one; LovyanGFX does not.

## 5. Bank identity IS the diff key

From the 2026-09-15 audit, and the single most important behavioural fact about this panel:

| previous bank | this push | what happens |
|---|---|---|
| fast | clean | full-screen GC16 -- a real scrub |
| clean | clean | only ink driven, white background skipped -> both pages at once, then an imprint |
| clean | fast | full-screen DU, scrubs nothing -> **ghosting** |
| fast | fast | true differential DU -- correct for page turns |

"Which waveform" and "how much of the screen" are not independent choices; they are the same
choice. **Any change that alters how often or in what order pushes happen is a ghosting change**,
even when it touches no waveform code.

## 6. Async: what it buys, and what it does not

`LgfxEpdDriver` historically called `settleDisplay()` after every push, discarding the overlap
`Panel_EPD` already offered. Splitting it (`displayStart`/`displayFinish`,
`supportsAsyncDisplay() -> true`) is device-validated: no wedge, no torn page.

**It does not make refreshes faster.** The destination screen still drains the waveform --
`displayBuffer()` opens with `syncPendingAsync()`. Measured on the reader's single-push path: the
display call drops 1559 ms -> ~200 ms, but the page turn only goes 1700 ms -> 1547 ms. The wait
moved into `completeDisplay()` rather than disappearing.

**What it buys is throughput.** The wait is now taken with the render lock released, so
`stepCurrentSectionBuild()` and the pre-render can use ~1.4 s per turn that was previously dead.
Device log shows whole section builds completing during reading.

Judge async work on throughput, never on latency.

## 7. THE TRAP: capability flips are behaviour flips

**This cost us a ghosting regression on 2026-09-22 and is the most important operational lesson in
this document.**

`supportsAsyncDisplay()` is not only a statement about the driver. Consumers branch on it:

```cpp
bool EpubReaderActivity::usesDeferredAa() const {
  return !(renderer.supportsAsyncRefresh() && !renderer.isX3());
}
```

Before the async split, `LgfxEpdDriver` returned **false**, so T5S3 used **deferred** AA. That was
deliberate -- the call site says so:

> This was `!renderer.isX3()`... On the T5S3 that is false twice over: LgfxEpdDriver does not
> override `supportsAsyncDisplay()` and so cannot overlap at all, yet the board took the inline
> path and paid the plane / gray flush / restore writes additively, with a blocking refresh
> underneath. **A suspected contributor to the ghosting seen there.**

Flipping the capability to true silently moved T5S3 back onto the inline path -- undoing a fix
whose whole mechanism was that the capability was false.

It compounds with the overlap change: background builds now run during reading and **borrow the
secondary buffer**, which makes grayscale capture unavailable, which makes `singlePushAaThisRender`
false, which routes those pages to inline AA. More builds during reading means that window opens
more often.

**Rule:** before changing what a `supports*()` predicate returns, grep every consumer and read the
comment at each call site. In this tree those comments record device findings, not restatements of
the code. A capability is an API contract *and* a behaviour switch.

## 8. Known-good invariants

- `waitDisplay()` alone is not a wait. Yield first.
- A dirty rect saves CPU, never waveform time.
- Never write `g_canvas` while a refresh may be in flight; `pushCanvas*` opens with
  `waitDisplay()` for that reason.
- Handing the **host** framebuffer back early is safe: `pushSprite()` copies the canvas into
  `Panel_EPD`'s own 4bpp buffer synchronously, and the refresh walks that buffer and
  `_step_framebuf`. This is also why `displayGrayscaleFrame()` deliberately skips `swapBuffers()`.
- Extra pushes re-tag the bank. See section 5.

## 9. Open questions

1. **The range-11 under-drive** (42 frames vs vendor 57). Cheapest real lead on residual ghosting.
   Needs the clean bank derived from the vendor GC16 phase count per range rather than from
   `3 x L[15]`.
2. **`usesDeferredAa()` needs a real predicate.** X3 is excluded by name, and T5S3 now needs the
   same treatment for a different reason. Neither exclusion is principled; both are empirical.
3. **The 128-block LUT budget** -- vendor constraint or LovyanGFX one? Unestablished.
4. **VCOM is a copied default**, never measured on this panel (from the 2026-09-15 audit).
5. **Would the epdiy backend be better?** It has source-aware LUTs and real area updates, both of
   which this panel could use. But it abandons the waveform generator, the clean/fast bank model
   and everything the 2026-09-15 audit established. A port, not a swap, and unmeasured.
